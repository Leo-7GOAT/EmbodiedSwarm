# Commissioning and telemetry (中文：硬件接入、标定与回放)

These tools prepare software commissioning. No robot-controller protocol, actuator parameter
or Raspberry Pi HIL result is assumed. `commissioning.example.json` leaves
unknown manufacturer and calibration values as `null`, and hardware disabled.

From the repository root, with its Python dependencies installed:

```bash
python -m tools.hardware.commission mock-step artifacts/commissioning_fixture.jsonl
python -m tools.hardware.commission measure artifacts/commissioning_fixture.jsonl
python -m tools.hardware.commission replay artifacts/commissioning_fixture.jsonl
python -m tools.hardware.commission inject-fault artifacts/commissioning_fixture.jsonl artifacts/commissioning_fault.jsonl --kind stale_state
python -m pytest -q tests/test_hardware_tools.py
```

`mock-step` is an explicit first-order **mock I/O fixture** for testing the analysis
pipeline. It does not run CARLA, measure hardware or certify an actuator. Output
files are create-only: use a fresh filename for each run. Analysis works with
real recordings generated by `Recorder` through a verified adapter. Specify a
channel and its unit when recording motor, steering or joint response.

`Recorder(path, mode, backend, clock)` records command, state, encoder, IMU,
receipt and fault events. Mode is one of `mock_io`, `replay`, `real_sim`,
`hardware`. Every file uses one provenance and one clock domain. Time is
nonnegative monotonic seconds; SI units belong in each event's `units` map.
Commands and receipts share `command_id` for measured roundtrip latency.
Cross-host one-way latency requires separately measured clock synchronization;
the tool does not infer it. Example integration:

```python
from tools.hardware.telemetry import Recorder
with Recorder("new_run.jsonl", "hardware", "verified_vendor_adapter", "host_monotonic") as log:
    log.write(0.0, "encoder", {"ticks": 42}, {"ticks": "count"})
    log.write(0.01, "imu", {"yaw": 0.02}, {"yaw": "rad"})
```

Step analysis reports sample-based 10–90% rise, time to 63%, tail mean gain and
overshoot. A steady tail and sufficiently long sampling window are required;
these estimates are inputs to subsequent model fitting. Zero response is an
identification failure. The tool never invents a successful response.

Offline replay validates sequence, chronology, provenance, units and finite
values. It sends no device commands. Fault injection produces a separate
`replay` file; it cannot turn an injected run into physical-validation evidence.
Use the project safety integration tests for proof of actual controller response.

## First hardware week

1. Obtain the exact base/arm/controller manual, wiring diagram, voltage,
   ground, polarity, command acknowledgement and disconnect semantics. Fill in
   a private copy of the configuration, keeping secrets outside Git.
2. Verify physical E-stop and independent power isolation. Elevate wheels; log
   encoder/IMU data and check axis signs before any closed-loop movement.
3. Execute bounded bidirectional joint/motor steps through the supervisor;
   log measured angle/speed, timestamps and acknowledgements. Estimate delay,
   deadzone, saturation, rate limit and first-order response; retain raw logs.
4. Verify stale-state, command-timeout, network-loss, manual override and
   geofence stop in a controlled area. A software stop is not a physical E-stop.
5. Begin low-speed tracking, compare simulation versus recorded measurements,
   fit parameters, then broaden speed/disturbance envelopes. Measure CPU,
   memory, control jitter and transport latency **on the target Pi**.

Deployment staging and rollback scripts are local, hardware-disabled operations.
Activation still requires verified configuration and physical commissioning.

After committing and verifying the repository, stage on the local deployment
host (the host must already have the simulator/test dependencies installed):

```bash
python -m tools.hardware.deploy --root ../embodiedswarm-releases stage
# Replace FULL_COMMIT_SHA with the 40-character SHA printed by stage.
python -m tools.hardware.deploy --root ../embodiedswarm-releases select FULL_COMMIT_SHA
python -m tools.hardware.deploy --root ../embodiedswarm-releases rollback
```

`stage` exports committed sources into a new release folder, builds an isolated
venv reusing installed host packages, installs this project without modifying
global dependencies, and runs its Python regression. Failed tests leave the
selection unchanged and retain the log. `--skip-tests` leaves a release
unselectable. Selection/rollback update an atomic software manifest and start no
process. Previous releases remain intact. Runtime launcher/supervisor owns safe
stop; switching software selection does not certify physical braking.

Linux/WSL profiling (psutil required):

python -m tools.hardware.profile --output artifacts/regression_profile.json -- python -m pytest -q

Measurements describe the recorded host; target-platform HIL remains pending.
